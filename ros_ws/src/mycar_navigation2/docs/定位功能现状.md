## 一、当前位置估计链路

### 1.1 整体结构

定位链路是**四层串联**结构，层与层之间只通过 ROS 话题和 TF 传递，**没有任何一处做多源联合优化**（无紧耦合、无图优化融合、无误差状态滤波）。

| 层 | 执行位置 | 是否启用 | 输入 | 输出 |
|---|---|---|---|---|
| 第 0 层：航迹推算 | MCU（ESP32），50 Hz | ✅ 启用 | 编码器脉冲、车体参数 | `/odom`、`/imu` |
| 第 1 层：EKF 融合 | 上位机，30 Hz | ❌ **未启用** | `/odom`、`/imu` | `/odometry/filtered`、TF `odom→base_link` |
| 第 2 层：odom 域 TF | 上位机，1000 Hz 循环 | ✅ 启用 | `/odom` | TF `odom→base_footprint` |
| 第 3 层：SLAM / 定位 | 上位机 | ✅ 启用（三选一） | `/scan` + TF | `/map`、TF `map→odom` |
| 第 4 层：导航避障 | 上位机 Nav2 | ✅ 启用 | `/scan`、`/map`、TF | `/cmd_vel` |

### 1.2 每一层在哪里融合、输入输出是什么

**第 0 层（MCU 内部，唯一真正被执行的"融合"）**
- 位置：ESP32 固件 `main/control/motion_controller.cpp`
- 周期：20 ms（50 Hz），由 `motion_task` 驱动
- 输入：双轮编码器计数增量、轮径 65 mm、轮距 131.7 mm
- 输出：`/odom`（`nav_msgs/Odometry`，50 Hz）、`/imu`（`sensor_msgs/Imu`，50 Hz）、`/scan`（10 Hz）
- 融合性质：**不是真正的多源融合**，详见第二部分——IMU 未参与位姿计算

**第 1 层（`ekf.yaml` 定义的 EKF，未启用）**
- 位置：`mycar_navigation2/config/ekf.yaml`
- 输入：`/odom`（x, y, z 位置 + 偏航角速度）、`/imu`（roll, pitch, yaw 姿态）
- 输出：`/odometry/filtered`、TF `odom→base_link`、`/accel/filtered`
- 状态：**没有任何 launch 加载它**

**第 2 层（`mycar_bringup` 节点）**
- 位置：`mycar_ws/src/mycar_bringup/src/mycar_bringup.cpp`
- 行为：订阅 `odom` 话题，把 pose 原样广播成 TF `odom → base_footprint`，**不做任何计算**
- 循环：`WallRate(1000.0)` + `spin_some`

**第 3 层（SLAM / AMCL）**
- GMapping：`/scan` + TF 链 → `/map` + TF `map→odom`
- Cartographer：`/scan`（+ 可选 TF）→ `/map` + TF
- AMCL（仅导航模式）：`/scan` + 静态地图 → TF `map→odom`

**第 4 层（Nav2）**
- 代价地图以 `/scan` 为唯一观测源，DWB 局部规划器输出 `/cmd_vel`

## 二、MCU 端的位置计算

代码位置：`leap_demo/leap_ros_mcu_driver/main/control/motion_controller.cpp`

### 2.1 编码器提供什么

- 左右轮各一个正交编码器（QuadratureEncoder），**4680 脉冲/转**
- 每 20 ms 读取计数增量 → pps → RPM → 一阶低通滤波（α = 0.35）→ `filtered_rpm_`
- 车体常量：轮径 **65 mm**，轮距 **131.7 mm**（半轮距 `kLy = 65.85 mm`）

### 2.2 差速运动学

```
vx = (vL + vR) / 2          (mm/s)
vy = 0                       (恒为 0，差速模型)
wz = (-vL + vR) / (2 * kLy)  (rad/s)
```

即车辆被当作**理想差速模型**，`/odom` 的 `twist.linear.y` 恒为 0。

### 2.3 位置怎么算（航迹推算）

```
odom_yaw_ += wz * dt                      // 航向由编码器角速度积分
pos_x_ += (vx*cos(yaw) - vy*sin(yaw)) * dt
pos_y_ += (vx*sin(yaw) + vy*cos(yaw)) * dt
```

这是标准的 **dead reckoning（航迹推算）**，误差随时间无界累积。

### 2.4 姿态怎么算

- `GetOdometry()` 返回的 yaw 就是 **编码器积分出来的 `odom_yaw_`**，不是 IMU 的 yaw
- `GetOdometryQuaternion()` 用这个 yaw 单独生成四元数（只有 `qw`、`qz` 非零，`qx = qy = 0`），即**假定车辆永远水平、只有偏航**
- 结果以 mm / mm·s⁻¹ 存放，发布到 ROS 时统一除以 1000 转成 m

### 2.5 IMU 提供什么 —— 关键结论

**IMU 不参与位置估计，也不参与姿态估计。**

`Update(dt, current_imu_yaw_rad)` 接收 IMU 的 yaw，但只做两件事：

1. 计算相对量 `imu_yaw_rel_ = current_imu_yaw_rad - yaw_offset_`
2. 把这个相对 yaw **只用于 MCU 内部的相对转向控制闭环**（`MoveRelative` 的转向阶段用它判断已转角度）

`odom_yaw_`、`pos_x_`、`pos_y_` 三个量的计算式里**完全没有 IMU 项**。

IMU 与里程计的唯一交互点是 `ResetOdometry()`：清零时置 `need_reset_yaw_offset_`，让下一次 `Update()` 重新采样一次 IMU yaw 偏置（`yaw_offset_`）——这只是**偏置初始化**，不是融合。

### 2.6 小结

| 量 | 来源 |
|---|---|
| 位置 x, y | 100% 编码器航迹推算 |
| 航向 yaw | 100% 编码器差速积分 |
| 姿态 roll, pitch | MCU 侧不计算（上位机 `/imu` 报文里带，但无人使用） |
| IMU 的作用 | 仅 MCU 本地相对转向控制反馈 |

## 三、上位机端的融合

### 3.1 EKF 有没有被启动？—— **没有**

逐一核对所有可能加载 `ekf.yaml` 的 launch：

| launch 文件 | 是否启动 EKF |
|---|---|
| `mycar_demo/launch/bringup_all.launch.py` | ❌ 只有 socat、micro_ros_agent、ydlidar、mycar_bringup |
| `mycar_bringup/launch/mycar_bringup.launch.py` | ❌ 只有 joint_state_publisher、robot_state_publisher、mycar_bringup |
| `mycar_navigation2/launch/navigation2.launch.py` | ❌ 只 include nav2_bringup 的 bringup_launch.py |
| `mycar_navigation2/launch/navigation2_rviz.launch.py` | ❌ 同上 + rviz2 |
| `mycar_navigation2/launch/slam_nav2.launch.py` | ❌ gmapping + nav2_bringup + rviz2 |
| `mycar_cartographer/launch/cartographer.launch.py` | ❌ cartographer_node + occupancy_grid_node + rviz2 |
| `slam_gmapping/launch/slam_gmapping.launch.py` | ❌ 单节点 |

**结论：`ekf.yaml` 是一份孤立配置**，只有手工执行 `ros2 run robot_localization ekf_node --params-file ...` 才会生效。

### 3.2 `ekf.yaml` 的配置内容（写了但没跑）

| 配置项 | 值 |
|---|---|
| 节点名 | `ekf_filter_node`（robot_localization） |
| 频率 | 30.0 Hz |
| `two_d_mode` | **false**（用 3D 全向模型，但无 3D 观测源） |
| `publish_tf` | true |
| `publish_acceleration` | true |
| `map_frame` / `odom_frame` / `base_link_frame` | `map` / `odom` / `base_link` |
| `world_frame` | `odom`（只做 odom 域局部融合） |
| `odom0` | `/odom`，融合 **x, y, z 位置** + **偏航角速度(vyaw)**，线速度全关 |
| `imu0` | `/imu`，只融合 **roll, pitch, yaw 姿态**，角速度与线加速度**全关** |

配置本身也有两处值得商榷：`two_d_mode: false` 却开着 **z 位置**融合（z 无独立观测源，协方差会持续膨胀）；IMU 的 `angular_velocity` 与 `linear_acceleration` 被完全关闭，IMU 沦为"电子水平仪"。

更关键的是：MCU 把 `/imu` 的三个协方差首元素都设成了 -1，robot_localization 的 `imuCallback()` 会因此整段忽略 IMU 的 orientation、角速度和线加速度。无论 `imu0_config` 怎么配，IMU 都不会参与融合。必须先改 MCU 固件。

### 3.3 实际使用的是哪条链路

```
MCU /odom  →  mycar_bringup  →  TF odom→base_footprint  →  SLAM / Nav2
```

即上层所有模块拿到的车体位姿，**就是裸的编码器航迹推算值**，没有经过任何滤波与多源融合。

### 3.4 `/odometry/filtered` 有没有在发？—— **没有**

因为 EKF 节点从未被启动，该话题不存在。

### 3.5 被浪费的资源

MCU 以 50 Hz 发布 `/imu`，但上位机侧**零消费者**：

- GMapping 参数中无任何 IMU 项
- Cartographer 两份 lua 均 `use_imu_data = false`
- 唯一能用它的 EKF 没启动

`/ultrasonic`（10 Hz）同样无消费者：两份 Nav2 参数的 `observation_sources` 都只有 `scan`。

## 四、SLAM 的融合

### 4.1 GMapping

配置：`slam_gmapping/params/slam_gmapping.yaml`，由 `slam_gmapping.launch.py` 单节点启动。

| 项 | 内容 |
|---|---|
| 输入（话题） | `/scan`（节点默认订阅名） |
| 输入（TF） | `odom → base_footprint`（`odom_frame: odom`、`base_frame: base_footprint`）——**走 TF 查，不订阅 `/odom` 话题** |

| 输出（TF） | `map → odom`（`transform_publish_period: 0.05` s，20 Hz） |
| 算法 | Rao-Blackwellized 粒子滤波，**30 粒子** |
| 关键参数 | `delta: 0.05` m、`maxUrange: 4.0` m、`maxRange: 6.0` m、`linearUpdate: 1.0` m、`angularUpdate: 0.5` rad、`iterations: 5`、`minimum_score: 0.0`、地图范围 ±10 m |

**无回环检测**，只能建小场景地图。

|---|---|---|

| `published_frame` | `laser_frame` | `odom` |
| `odom_frame` | `odom` | `odom` |
| `provide_odom_frame` | **true**（Cartographer 自己发 odom 分支） | **false** |
| `use_odometry` | **false（不用里程计）** | **true** |
| `use_imu_data` | **false（不用 IMU）** | **false** |

| 有效距离 | 0.10 – 5.5 m | 0.10 – 3.5 m |

- 两者都没有任何参数指向 `/odometry/filtered`

- Cartographer 默认配置连里程计都不用（`use_odometry: false`）

## 五、TF 树

### 5.1 当前实际 TF 树

```
map
 └── odom                     ← GMapping / AMCL / Cartographer（三选一发布 map→odom）
      └── base_footprint      ← mycar_bringup 节点（来自 /odom 的 pose）
           └── base_link      ← robot_state_publisher（URDF 固定变换，z = +0.076）
                ├── laser_frame     ← URDF，z = +0.075
                ├── imu_link        ← URDF，z = +0.02
                ├── left_wheel_link ← URDF，y = +0.10，z = -0.06（continuous joint）
                ├── right_wheel_link← URDF，y = -0.10，z = -0.06（continuous joint）
                └── caster_link     ← URDF，x = +0.06，z = -0.076
```

### 5.2 每个 TF 谁发

| TF | 发布者 | 状态 |
|---|---|---|
| `map → odom` | GMapping（建图时）/ AMCL（`mycarbot.yaml`，导航时）/ Cartographer（Cartographer 模式） | ✅ 三选一 |
| `odom → base_footprint` | **`mycar_bringup` 节点** | ✅ 启用 |
| `odom → base_link` | EKF（`ekf.yaml` 配置 `publish_tf: true`） | ❌ **无人发布**（EKF 未启动） |
| `base_footprint → base_link` | `robot_state_publisher`（URDF，fixed，z = +0.076） | ✅ 启用 |
| `base_link → laser_frame / imu_link / 各轮 / caster` | `robot_state_publisher`（URDF 静态变换） | ✅ 启用 |

注意：MCU 在 `/odom` 报文中声明 `child_frame_id = base_link`，但上位机**没有任何节点按这个声明广播 TF**，实际广播的是 `base_footprint`。

### 5.3 frame 名冲突 —— 有，且不止一处

1. **`base_link` 与 `base_footprint` 混用**
   - GMapping 用 `base_footprint`
   - AMCL（`mycarbot.yaml`）用 `base_link`；`nav2.yaml` 的 AMCL 又用 `base_footprint`
   - EKF 用 `base_link`；MCU `/odom` 声明 `base_link`
   - URDF 中两者存在 **7.6 cm 固定高度差**

2. **`/odom` 语义被改写**
   MCU 声明该 pose 属于 `base_link`，`mycar_bringup` 却把它当作 `base_footprint` 广播，导致 `base_link` 实际高度被额外抬升 7.6 cm。

3. **Cartographer 抢 odom 分支（严重）**
   默认 lua 的 `provide_odom_frame: true` 会让 Cartographer 自己发布以 `odom` 为父的变换，与 `mycar_bringup` 的 `odom → base_footprint` 并存，造成 `odom` 出现两个父级来源。改用 `mycar_2d.lua`（`provide_odom_frame: false`）才不会冲突，但那份不是默认。

4. **`tracking_frame: laser_frame`**
   Cartographer 直接以雷达为跟踪基准，雷达与 `base_link` 有 0.075 m 高度差，2D 模式下影响有限但语义不干净。

### 6.4 配置之间的冲突

1. **`use_sim_time` 不一致（高风险）**
   `mycarbot.yaml` 中几乎所有节点的 `use_sim_time` 均为 **True**；`nav2.yaml` 全为 False；launch 传入的是 `false`。
   Nav2 的 `bringup_launch.py` 是否会覆盖嵌套在 `amcl.ros__parameters` 下的 `use_sim_time`，**已确认：会覆盖** —— `bringup_launch.py` 用 `RewrittenYaml` 递归替换所有层级的 `use_sim_time` 叶子键，所以 `mycarbot.yaml` 里的 `True` 会被 launch 传入的 `false` 覆盖。AMCL 不会卡在仿真时钟。该项从"必须修 bug"降级为"防御性清理"。

2. **AMCL 的 base_frame 与实际 TF 链不匹配**
   `mycarbot.yaml` 的 `base_frame_id: base_link`，而实际链为 `odom → base_footprint → base_link`，能连通但多一跳且语义错位。

3. **Cartographer `provide_odom_frame: true` 与 `mycar_bringup` 的 odom 广播冲突**（见 5.3）。

4. **"一键启动"脚本与编译的驱动包不一致**
   `bringup_all.launch.py` 用 YDLIDAR，源码包是 `camsense_lidar`。

5. **`bringup_all.launch.py` 未启动 SLAM / Nav2 / EKF**
   它只完成"通信 + 雷达 + TF"，定位与导航需另行启动。

## 七、和工业方案的差距

### 7.1 工业常见做法

- **多源进滤波器**：轮式里程计 + IMU +（激光/视觉）里程计统一进 EKF / 误差状态卡尔曼滤波（ESKF）。IMU 提供高频角速度与加速度做**状态预测**，里程计提供**速度观测**，激光/视觉提供**位姿观测**
- **双 EKF 架构**：`robot_localization` 跑两个实例，分别维护 odom 域（连续、无跳变）与 map 域（融合全局观测）
- **SLAM 端**：带回环优化的图优化（Cartographer、LIO-SAM）或紧耦合 LIO（FAST-LIO2 / FAST-LIVO2）
- **冗余与故障诊断**：传感器失效可切换、有协方差可观测性判据

### 7.2 本项目少了什么

1. **EKF 没跑** —— 整条链路没有任何滤波器（最大缺口）
2. **IMU 完全没用上** —— 既不进里程计，也不进 SLAM，等于白装
3. **单源位姿、无冗余** —— 打滑或编码器丢脉冲时误差直接累积且无法察觉；航向为纯积分，几分钟即明显漂移
4. **Cartographer 关掉里程计与 IMU** —— `use_odometry: false`、`use_imu_data: false`，退化为纯扫描匹配，快速旋转易跟丢
5. **GMapping 无回环** —— 30 粒子、±10 m 地图边界，仅适合小场景
6. **超声波未进代价地图** —— 近距离盲区无兜底
7. **时间戳与 frame 体系不干净** —— `use_sim_time` 混杂、`base_link` / `base_footprint` 混用、`provide_odom_frame` 冲突

### 7.3 改进优先级

## 八、待确认的问题

以下内容基于现有材料**无法确定**，需要实测或补充阅读：

1. **Nav2 的 `bringup_launch.py` 是否会覆盖嵌套的 `use_sim_time`？**
   `mycarbot.yaml` 中 `amcl.ros__parameters.use_sim_time: True` 而 launch 传 `false`。若不被覆盖，AMCL 时间体系会错乱。**需阅读 `nav2_bringup` 包源码确认**（本次未读）。**已确认：会覆盖。**

2. **`ekf.yaml` 是否曾以其他方式启动过？**
   例如手工 `ros2 run`、或某个未纳入本次读取范围的脚本/别名/系统服务。可实测验证：系统运行时执行 `ros2 node list` 查看是否存在 `/ekf_filter_node`，`ros2 topic list` 查看是否存在 `/odometry/filtered`。

3. **实际使用的雷达究竟是哪一个？**
   `bringup_all.launch.py` 启动 `ydlidar_ros2_driver`（socat 把 UDP 8889 转成 `/dev/lidar`），而源码包是 `camsense_lidar`，`install/` 中还残留 `ldlidar_stl_ros2`。**不确定**当前物理接的是哪款雷达、哪条路径是真正在用的。

4. **Cartographer 实际运行时是否真的产生了 TF 冲突？**
   `provide_odom_frame: true` 与 `mycar_bringup` 同时发布以 `odom` 为父的变换，理论上冲突，但实际是否运行过该 launch、冲突表现如何，**未实测**。

5. **AMCL 是否真的正常工作？**
   在 `slam_nav2.launch.py`（gmapping + nav2）中，GMapping 与 AMCL 会**同时**尝试发布 `map → odom`，二者是否冲突、谁生效，**不确定**（取决于 `tf_broadcast` 与实际启动顺序）。

6. **`/imu` 的协方差是否被填充？**
   MCU 侧 `publish_imu()` 只填了四元数、角速度、加速度，**未填协方差矩阵**（实际是把三个协方差数组的首元素设为 -1）。robot_localization 对零协方差的处理行为（是否有默认值、是否报错）**不确定**。**已确认：三个 -1 会被整段忽略。**

7. **`/odom` 的协方差是否被填充？**
   同上，MCU 侧未显式填写 `pose.covariance` 与 `twist.covariance`，EKF 启用后需要评估其影响。**已确认：全 0 会被替换成极小值，等于完全信任。**

8. **URDF 中的 `base_footprint → base_link` 7.6 cm 偏移是否为有意设计？**
   与 `/odom` 声明的 `base_link` 语义叠加后，车体高度可能被重复计入，**需实测 TF 树验证**。

9. **`mycarbot.yaml` 中 AMCL 缺少 `scan_topic` 显式配置（`nav2.yaml` 也没有）**
   Nav2 的默认值与重映射行为**不确定**，实际订阅的话题名需实测确认。
