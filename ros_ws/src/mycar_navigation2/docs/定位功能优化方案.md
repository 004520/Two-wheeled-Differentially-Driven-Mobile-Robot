## 已确认的关键结论

> 以下结论已通过静态查证确认（本机只读 + 上游源码比对），落地前可直接据此调整方案。
> 本机 ROS 2 发行版 = **humble**。

### IMU 会被整段忽略（关键，影响优化项 1）

- `robot_localization` 的 `imuCallback()` 中有三处判断：只要 `orientation_covariance[0]`、`angular_velocity_covariance[0]`、`linear_acceleration_covariance[0]` 中**任意一个等于 -1**，就**整段忽略**对应分量（源码注释原文：`Ignoring orientation...` / `Ignoring angular velocity...` / `Ignoring linear acceleration...`）。
- MCU 正好把这三个都设成了 **-1.0**（`microros_task.cpp` 484–486 行）。
- **后果：无论 `ekf.yaml` 里的 `imu0_config` 怎么配，IMU 都不会参与融合。** 不修这一项，启动 EKF 后输出基本等于"裸 odom 的平滑版"，A5/A6 不会改善。
- **处理：必须先改 MCU 固件**，把三个协方差改成合理值（不能是 -1，也不能全 0）。
- **这是优化项 1 的前置硬依赖**（原本列的"补协方差"是 P2 可选项，现提升为 P0 前置）。

### 零协方差的处理

- `/odom` 的零协方差**不会报错、不会被丢弃** —— `copyCovariance()` 会把它**替换成一个小值**以维持滤波器稳定，并产生一条 WARN 诊断。
- 但替换值很小 → EKF **几乎完全信任 `/odom`**，IMU 权重被压到接近 0。
- **处理：`/odom` 也要补真实协方差**（`pose.covariance` / `twist.covariance`），不能依赖这个兜底。
- 注：替换的具体数值本次未定位到确切赋值语句（**不确定**）；从 `filter_base.cpp` 可见滤波器内部有 `covariance_epsilon_ = I × 0.001`，量级应在 1e-3～1e-6 之间。

### `/amcl_pose` 确认会发布

- `nav2_amcl` 的 `initPubSub()` 中**无条件**创建 publisher：`create_publisher<PoseWithCovarianceStamped>("amcl_pose", LatchedPublisherQoS())`，**没有任何开关参数**；`tf_broadcast` 只控制 TF 发布，与话题无关。
- **但必须先给初始位姿**：`publishAmclPose()` 开头判断 `initial_pose_is_known_`，否则只打 WARN（`Please set the initial pose...`）且**不发数据** —— 话题存在但为空。
- **发布时机不固定**：仅在 `resampled || force_publication || !first_pose_sent_` 时发布，跟随 `update_min_a`(0.2 rad) / `update_min_d`(0.25 m) / `resample_interval`(1) —— 运动越频繁越密，静止时基本不发。
- **对双 EKF 的影响**：`pose0` 要考虑时间戳滞后与 `pose0_differential` 设置（详见优化项 9）。

### 顺带确认

- `nav2_amcl` 源码中 `base_frame_id` 的**默认值就是 `"base_footprint"`** → **优化项 2 统一到 `base_footprint` 的方向是对的**（`mycarbot.yaml` 里显式写的 `base_link` 属于偏离默认值）。
- `robot_localization` 的 `print_diagnostics` 默认 **false**，而"协方差为零/为负""IMU 被忽略"这些 WARN 只在它为 true 时才通过 `/diagnostics` 发布 → **调试期建议显式设为 true**。
- `two_d_mode: true` 时 `forceTwoD()` 会把 3D 分量的协方差设为 **1e-6**、测量置 0 → 与"开 two_d_mode、关 z 融合"的建议一致。
- `nav2_bringup` **会递归覆盖**所有层级的 `use_sim_time`（详见优化项 3），`yaml_filename` 同理被覆盖。

## 二、优化项列表

### 优化项 1（P0）：启动 EKF 并修正融合配置

**优化内容**

1. **【前置硬依赖】先改 MCU 固件**：把 `/imu` 的 `orientation_covariance`、`angular_velocity_covariance`、`linear_acceleration_covariance` 首元素由 **-1** 改为合理值（见下方"前置硬依赖"）
2. 在一个 launch 中加载 `ekf.yaml`，真正启动 `robot_localization` 的 `ekf_filter_node`
3. 修正 `ekf.yaml`：`two_d_mode` 改 `true`、关闭 `z` 位置融合、IMU 改提供**偏航角速度**、`print_diagnostics` 改 `true`
4. 处理 `/odom` 协方差未填充的问题
5. 统一 frame 命名（与优化项 2 配套）

**为什么优化（对应现状问题）**

- 现状 三.1 / 三.3：整条链路**没有任何滤波器**，上层拿到的就是编码器裸积分值，误差无界累积且无法察觉。
- 现状 三.2：`two_d_mode: false` 却开着 `z` 位置融合 —— 地面小车无高度观测源，`z` 协方差持续膨胀，浪费算力并污染估计。
- 现状 三.2：IMU 只贡献 `roll/pitch/yaw`、角速度与线加速度全关 —— IMU 沦为"电子水平仪"，最擅长的高频角速度信息完全浪费。
- 现状 二.3：航向是纯编码器积分，打滑即漂移且无法自愈；陀螺短期精确，正好互补。

**前置硬依赖：IMU 协方差必须先改（已确认）**

- `robot_localization` 的 `imuCallback()` 判断：三个协方差数组中只要首元素为 **-1**，就整段忽略对应分量。
- MCU 当前把 `orientation_covariance`、`angular_velocity_covariance`、`linear_acceleration_covariance` 的 `[0]` **全部设为 -1.0**。
- **因此：不先改固件，本优化项无法让 IMU 参与融合**，配置 `imu0_config` 不会有任何效果。
- 修改点：`microros_task.cpp` 中这三行 -1.0 → 按传感器手册填合理方差（例如陀螺 ~1e-4、加速度 ~1e-2、姿态按 IMU 输出精度给），**不能填 0**（0 会被替换成极小值，等价于"完全信任"）。
- 代价：需 ESP-IDF 编译 + 烧录（与优化项 8 同批做更划算）。

**重要说明（与原需求的偏差，请确认）**

1. **不建议开启 IMU 的线加速度（`ax/ay/az`）**
   - `robot_localization` 在 `two_d_mode` 下本就不推荐融合线性加速度；
   - MCU 侧 `publish_imu()` 直接把加速度乘 9.80665 发布，**不确定**是否做了重力去除与零偏标定。若含重力分量，滤波器会当成持续加速度，导致速度与位置迅速发散；
   - 建议先不开，待 A5/A6 达标后再做 A/B 对照实验。

2. **不建议开启 IMU 的绝对 `yaw`**
   - 固件 IMU 为 LSM6DS3（6 轴：加速度 + 陀螺），**没有磁力计**，其 yaw 只能由陀螺积分得到，长时间必然漂移；作为绝对观测量喂给 EKF 会与编码器积分 yaw 互相拉扯；
   - 因此让 IMU 只提供**角速度 `vyaw`**（短期精确），绝对 yaw 仍由编码器提供（长期稳定）；
   - **不确定**：`imu.GetYaw()` 是否为 DMP 融合输出、是否有零偏补偿，需向固件负责人确认（Q1）。

**协方差未填充的处理（现状 八-6、八-7）**

- 现状：MCU 侧未填 `/odom` 的 `pose.covariance` / `twist.covariance`；`/imu` 的三个协方差首元素被设为 **-1.0**。
- **已确认（静态查证）**：
  - **-1 是最严重的问题** → RL 会**整段忽略** IMU 的 orientation / 角速度 / 线加速度（见"前置硬依赖"）；
  - **全 0 不会报错** → 被替换成小值继续参与融合，但等价于"几乎完全信任该源"（`/odom` 会压制 IMU）。
- **因此处理顺序调整为：固件补协方差由 P2 提升为 P0 前置**：
  1. **必做（前置）**：`microros_task.cpp` 中把 IMU 三个协方差的 -1 改成合理值；
  2. **强烈建议（同批做）**：`publish_odom()` 补 `pose.covariance` / `twist.covariance`；
  3. **上位机兜底（本次做）**：`ekf.yaml` 显式配置 `process_noise_covariance` 与 `initial_estimate_covariance`；
  4. **排障开关**：`print_diagnostics: true`，用 `/diagnostics` 观察是否仍有 `*_covariance` 告警。

**预期效果**

- `/odometry/filtered` 以 50 Hz 输出滤波后位姿，抖动显著小于裸 `/odom`
- 原地旋转、短时打滑时航向误差明显下降（A6）
- 为优化项 9（双 EKF）预留标准接入点

**为什么优化（对应现状问题）**

- 背景（为什么放弃 XRCE 时间同步）：
  - `rmw_uros_sync_session()` 算出的 `session->time_offset` 会被**迟到回包**污染（旧 t0/t1/t2 + 新 t3），误差 = 陈旧时长 / 2（可达秒级）；
  - `process_timestamp_reply()` **无条件**写 offset，不判质量；`drain_udp_rx()` 只能清已到达 socket 的包，清不掉在途包；
  - MCU 侧无 SNTP / 无 RTC，`esp_timer` 只有自启动时间 → **MCU 无法自证 offset 是否正确**；
  - 表现为「offset 稳定自洽、`epoch − local == offset`，但发布出去的时间戳偏差 1–2 s」，且 MCU 侧发现不了。
- 核心改动：
  - 新增 `sntp_time_sync_once()`：向上位机 `192.168.0.59` 的 chrony 校时（`esp_netif_sntp_init` + `esp_netif_sntp_sync_wait`，超时 10 s，`smooth_sync = false`）；
  - SNTP 成功后 ESP-IDF 调用 `settimeofday()`，取 `gettimeofday()` 的墙钟与 `esp_timer_get_time()` 之差 → 反推 `s_epoch_offset_ms`（`current_epoch_millis()` 为 `esp_timer + offset`，无需改动即输出真墙钟）；
  - `create_ros_entities()` 与 `maybe_resync_epoch()` 加 `s_sntp_synced` 判断 → **停用 XRCE 时间同步**（既避免污染正确 offset，也让主循环不再被同步阻塞，`/odom` 恢复 50 Hz）；
  - 同步成功后 `esp_netif_sntp_deinit()`，避免后续周期硬跳变打乱 micro-ROS 的 `uxr_millis()` 心跳/超时；
  - 失败时自动回退到原有 XRCE 时间同步路径，**零回归**。
- 上位机配套：chrony 已配置为 NTP 服务器，监听 `0.0.0.0:123`，`allow 192.168.0.0/24`（虚拟机 `192.168.0.59`，小车 `192.168.0.110`，同网段）。
- 验证结果：
  - `/odom` 时间戳 `1790165166.17`，落在两次 `date` 之间，偏差 < 1 s；
  - `/imu` 时间戳 `1790165212.42`，落在两次 `date` 之间，偏差 < 1 s；
  - 不再出现 `epoch sync ok` / `periodic time sync failed`（XRCE 同步已停用）；
  - MCU 日志出现 `SNTP synced from 192.168.0.59: epoch=..., local=..., offset=...`。
- 遗留问题：无
- 后续注意：SNTP 只在启动时校时一次，之后靠 `esp_timer` 外推；晶振漂移约 ppm 级（≈3 ms/小时），远低于 100 ms 门槛。若需长时间高精度，可再加「每 30 分钟重新 init + sync_wait 一次」（此时跳变仅几 ms，安全）。

### 优化项 5（P1）：超声波进入局部代价地图

**为什么优化（对应现状问题）**

**改哪些文件**

| 文件 | 动作 | 是否核心代码 |
|---|---|---|

**建议配置值**（插件可用时）

**预期效果**

- 近距障碍（低于雷达盲区）可被感知并标记，降低低速碰撞概率

**风险**

### 优化项 8（P2）：MCU 侧用 IMU 抑制航向漂移

**优化内容**

在 `motion_controller.cpp` 的 `Update()` 中，把 IMU 偏航角速度（或相对 yaw）以互补滤波 / 加权方式引入 `odom_yaw_` 的更新。

**为什么优化（对应现状问题）**

- 现状 二.3：`odom_yaw_` 是纯编码器差速积分，打滑、地面不平、轮径误差都会直接变成航向误差且无法自愈。
- 现状 二.5：IMU 的 yaw 目前只用于 MCU 内部相对转向控制，**完全不进入位姿计算**。
- 陀螺短时间内角速度精确，正好补编码器打滑时的失效。
- **但这是固件改动，需重新编译与烧录**，成本显著高于上位机配置改动。

**重要建议：优先用优化项 1 解决，本项后置**

在上位机 EKF 里开 `imu0` 的 `vyaw`（优化项 1）**已在滤波器层面实现同样的互补效果**，可随时调参、不影响运动控制。因此：

- **推荐路径**：先做优化项 1（含其 P0 前置 1a），用 A6 验证效果；
- **仅当** A6 不达标、且确认瓶颈在 MCU 侧航向积分（例如打滑时 `/odom` 的 yaw 明显失真）时，再做本项；
- **补充**：由于优化项 1a 已经需要编译+烧录固件，**本项与 1a 同批实施可省一次烧录**；但本项会改动运动控制逻辑（回归风险更高），仍建议先单独验证 1a 的效果再决定。

**改哪些文件**

| 文件 | 动作 | 是否核心代码 |
|---|---|---|
| `leap_demo/leap_ros_mcu_driver/main/control/motion_controller.cpp` | 修改 `Update()` 中 `odom_yaw_` 的更新逻辑 | **是（固件）**——但不属于 `mycar_bringup` / SLAM 包 |
| `leap_demo/leap_ros_mcu_driver/main/msg/imu_msg.h` | 可能需要陀螺 z 字段（`ImuMsg` 已有 `gyro_z`，**不确定**是否已被填充，U5） | 是（固件） |
| `leap_demo/.../tasks/network/microros_task.cpp` | 若采纳"补协方差"，在 `publish_odom()` / `publish_imu()` 中补填协方差 | 是（固件） |
| 上位机 `ekf.yaml` | 若 MCU 已融合 IMU，需重新评估 `imu0` 配置，避免**重复融合 IMU** | 否（配置） |

**建议做法（互补滤波示意）**

- 用陀螺 z 积分得到高频航向增量，用编码器 yaw 做低频校正：`yaw = α·(yaw + gyro_z·dt) + (1-α)·encoder_yaw`，α 从 0.9 起步；
- 更稳妥：保留 `odom_yaw_` 不变，仅在与编码器差值超阈值时做软修正；
- **务必**处理单位（固件内陀螺为 deg/s，需转 rad/s）与 IMU 零偏（静止时标定 `gyro_z` 偏置）。

**预期效果**

- 打滑 / 原地转向时 MCU 侧航向更准，进一步改善 A6
- 上位机 EKF 拿到质量更高的 `/odom`

**风险**

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R8-1 | 需要 ESP-IDF 编译与烧录环境、物理接触小车 | **高**（成本） | 确认环境与权限后再启动；优先走优化项 1 |

### 优化项 9（P2）：双 EKF 架构（map 域第二个 EKF 实例）

**优化内容**

在优化项 1 的 odom 域 EKF 之上，增加**第二个 EKF 实例**维护 `map` 域：融合 `/odometry/filtered`（连续里程计）与 AMCL / SLAM 的全局位姿观测，输出平滑的 map 域位姿。

**为什么优化（对应现状问题）**

- 现状 7.1：工业常见做法是双 EKF —— 一个维护 odom 域（连续、无跳变），一个维护 map 域（融合全局观测）。
- 现状 7.2-1、7.2-3：本项目目前只有"裸编码器 → TF"一条路，且**没有任何滤波器**。即便做完优化项 1，也只是 odom 域干净了；`map → odom` 仍由 AMCL / GMapping 直接发布，全局定位跳变（AMCL 重采样会导致位姿突跳）会直接传给下游，造成规划的抖动。
- 第二个 EKF 可以**吸收全局观测的跳变**，输出时间上连续、平滑的 map 域位姿，这是提高导航鲁棒性的标准手段。

**改哪些文件**

| 文件 | 动作 | 是否核心代码 |
|---|---|---|
| 新建 `mycar_navigation2/config/ekf_map.yaml` | **新建**：第二个 EKF 的参数 | 否（配置） |
| 新建 `mycar_navigation2/launch/ekf_map.launch.py` | **新建**：启动第二个 EKF | 否（launch） |
| `mycar_navigation2/param/mycarbot.yaml` | 若由第二个 EKF 发布 `map → odom`，需把 `amcl.tf_broadcast` 设为 `false` | 否（配置） |

**建议配置值（示意）**

| 参数 | 建议值 | 理由 |
|---|---|---|
| `world_frame` | **`map`** | 与 odom 域 EKF 的关键区别 |
| `odom_frame` / `base_link_frame` | `odom` / `base_footprint` | 与优化项 2 一致 |
| `odom0` | `/odometry/filtered` | 用第一个 EKF 的输出作为连续预测源 |
| `pose0` | `/amcl_pose`（AMCL 发布的 `PoseWithCovarianceStamped`） | 全局观测源 |
| `pose0_differential` | `false` | 需要绝对位姿来约束 map 域漂移 |
| `publish_tf` | `true`（则需关掉 AMCL 的 `tf_broadcast`）**或** `false`（保留 AMCL 发 TF） | **二选一，必须避免双发**（见风险 R9-1） |
| `frequency` | 30.0 | 全局观测频率低，30 Hz 足够 |

**已确认：`/amcl_pose` 会发布，但有触发条件（U7 已收敛）**

- `nav2_amcl` 的 `initPubSub()` 中**无条件**创建 publisher：`create_publisher<PoseWithCovarianceStamped>("amcl_pose", LatchedPublisherQoS())`，**没有任何开关参数**；`tf_broadcast` 只管 TF 发布，与话题无关 —— **关掉 `tf_broadcast` 交给第二个 EKF 发 TF 后，`/amcl_pose` 照常可用** ✅
- **触发条件 1：必须先有初始位姿**。`publishAmclPose()` 开头判断 `initial_pose_is_known_`，否则只打 WARN（`Please set the initial pose...`）且**不发数据** → 话题存在但为空。需先发 `/initialpose`，或配置 `set_initial_pose` / `initialize_at_saved_pose`。
- **触发条件 2：发布时机不固定**。仅在 `resampled || force_publication || !first_pose_sent_` 时发布，跟随 `update_min_a`(0.2 rad) / `update_min_d`(0.25 m) / `resample_interval`(1) → **运动越频繁越密，静止时基本不发**。
- **对 `pose0` 的时间戳处理**：
  - 该话题是**低频、非周期、带滞后**的观测（stamp 用的是激光帧时间），第二个 EKF 必须容忍时间戳滞后；
  - 建议先用 `pose0_differential: false` 保留绝对约束，若出现跳变再改 `true` 做 A/B 对照；
  - 必要时设 `pose0_queue_size`、`transform_timeout`，并确认 `sensor_timeout` 大于 AMCL 的发布间隔（否则长时间静止会被判为超时、转为纯预测）。
- 顺带确认：源码中 `base_frame_id` 默认值就是 `"base_footprint"` → 优化项 2 的方向正确。

**预期效果**

- 全局定位跳变被平滑，导航路径更稳定（改善 A9）
- 形成标准"odom 域 + map 域"双层架构，便于后续接入 GPS、视觉等新观测源

**风险**

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R9-1 | 第二个 EKF 与 AMCL **同时**发布 `map → odom`，造成双父冲突 | **高** | 二选一：EKF 发则 `amcl.tf_broadcast: false`；或 EKF `publish_tf: false` |
| R9-2 | 融合 AMCL 位姿后与 `map → odom` 形成反馈回路（AMCL 自身又依赖 TF），可能自激 | **中高** | 需仔细设置 `pose0_differential` / `pose0_relative`；先做静态与慢速验证 |
| R9-3 | 配置复杂度上升，排障难度增加 | 中 | 只在优化项 1–4 全部稳定后再引入；保留"单 EKF"可回滚 |
| R9-4 | `robot_localization` 是否可用多个实例、命名空间冲突 | 低 | 用不同节点名与命名空间启动 |
| R9-5 | **未设初始位姿 → `/amcl_pose` 一直无数据**（已确认的触发条件） | **高** | 启动后先发 `/initialpose` 或配置 `set_initial_pose`；用 `ros2 topic echo /amcl_pose` 确认有数据再依赖它 |
| R9-6 | `/amcl_pose` 低频且带滞后，静止时基本不发 → `pose0` 长期无更新，滤波器转为纯预测 | 中 | 调大 `sensor_timeout`；必要时降低 `update_min_a/d` 提高发布密度；离线用 bag 验证 |

**验证方法**

```bash
ros2 node list | grep ekf                     # 应看到两个 EKF 节点
ros2 topic list | grep -i filtered
ros2 run tf2_tools view_frames                # 确认 map→odom 只有一个发布者
ros2 run tf2_ros tf2_echo map odom
# 确认全局观测源话题存在（没设初始位姿时这里会一直无输出）
ros2 topic list | grep -i amcl
ros2 topic echo /amcl_pose --once

# 若没有数据，先给初始位姿（地图坐标系下的位姿）
ros2 topic pub /initialpose geometry_msgs/msg/PoseWithCovarianceStamped \
  "{header: {frame_id: map}, pose: {pose: {position: {x: 0.0, y: 0.0}, orientation: {w: 1.0}}}}" --once

# 关键负向验证：让 AMCL 重新定位（触发跳变），观察第二个 EKF 输出是否平滑
```

6. **优化项 8 应最后评估**：若优化项 1 已让 A6 达标，本项可**直接不做**；若做，必须同步调整 EKF 配置避免重复融合 IMU（R8-3）。

### 3.5 建议的最小落地批次

- **批次一（必做）**：阶段 0 → 1 → 2 → 3。做完这一批，定位从"裸编码器"升级为"EKF 滤波 + IMU 参与"，收益最大。
