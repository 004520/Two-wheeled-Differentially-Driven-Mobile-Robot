## 1. P0-1 方位角系统性偏差

### 问题
正前方目标（方位真值 0°）被报成**偏左**：

| 场景 | 改动前 | 改动后 |
|---|---|---|
| bottle @0.5 m，正前方 | azimuth **−3.00°**（误差 −3.00°） | **−0.00°**（误差 −0.00°） |
| person @2.5 m，正前方 | azimuth **−5.00°**（误差 −5.00°） | **−0.00°**（误差 −0.00°） |
| bottle @1.0 m，偏左 20° | — | **+20.00°**（误差 −0.00°） |

偏差量正好等于目标**角宽的一半**（瓶子@0.5m→3°，行人@2.5m→5°）。

### 原因
`range_statistic: "min"` 分支用 `np.argmin(range)` 取最近回波，**并采用该 bin 自己的角度**：

```python
index = int(np.argmin(valid_ranges))
value = float(valid_ranges[index])
theta = float(valid_angles[index])   # ← 用了 argmin 那个 bin 的角度
```

刚性目标正对过来时，其前表面是一段**等距回波序列**（瓶身/人体正面在同一距离）。
`np.argmin` 在等值情况下返回**最小索引**，也就是物体在角度序列中的**右边缘**，
于是方位被系统性拉向右侧（REP-103 下表现为 −半角宽）。

### 修法
1. `config/vision_radar_fusion.yaml`：`range_statistic: "min" → "percentile"`（并补充根因注释）。
2. `vision_radar_fusion.py`：`declare_parameter("range_statistic", ...)` 默认值同步改为 `"percentile"`。
   > 必须同步：`ros2 run` 裸起不加载 yaml，否则默认值仍是 `"min"`，会踩同一个坑。

`percentile` 分支用**窗口内百分位距离**（默认 20）+ **窗口内角度均值**，对"等距回波带"不敏感：

```python
value = float(np.percentile(valid_ranges, self.range_percentile))
theta = float(np.mean(valid_angles))     # ← 用窗口中心，而非边缘
```

`"min"` 分支保留，仅供对比/回滚。

### 验证结果
正前方目标方位归零；带角度目标（+20°）不失真。**通过**。数值见上表。

## 2. P0-2 person 单目饱和 + block 单目不可用

### 问题
雷达没命中而回落到单目时，会输出** planner 会当真** 的错误距离：

| 场景（雷达关闭） | 改动前 | 改动后 |
|---|---|---|
| person @1.0 m | 2.830 m（**+183.0%**） | **DROPPED**（`mono_clipped`） |
| person @2.5 m | 3.347 m（**+33.9%**） | **DROPPED**（`mono_clipped`） |
| blue_block @0.8 m（框 +1 px 抖动） | 0.778 m（−2.8%） | **DROPPED** |
| blue_block @2.0 m（框 +1 px 抖动） | 1.865 m（**−6.7%**） | **DROPPED** |
| person @5.0 m（框未触边） | 5.000 m（−0.0%） | 5.000 m（−0.0%）← **未误杀** |

### 原因
单目测距公式 `Z = fy * H / h_pixel` 有两个致命假设：

1. **框高必须完整。** person 距相机 <3.5 m 时头顶就超出画面上边界，
   检测框被**裁掉**，`h_pixel` 偏小 → `Z` 偏大。人站在 1 m 处被读成 2.83 m。
2. **框高必须能分辨目标高度。** 5 cm 的 block 在 2 m 处只有约 14 px 高，
   检测框 ±1 px 抖动就是 ±7% 距离误差（1.4 m 外仅 <10 px，误差进一步放大）。

而 `_parse_heights()` 从 `dict(DEFAULT_REAL_HEIGHTS)` 起步，**从 yaml 里删掉 block 不生效** ——
所以「靠 `object_heights` 注释掉 block」这条路是走不通的，必须显式加类别白名单。

另外确认：下游 `avoidance_decider` **不使用** `det.id` 和 `score`（只看 `class_id` + bbox 中心），
因此「降低置信度/降权」对下游无效 —— 只能**丢弃**。

### 修法（`vision_radar_fusion.py`）
1. 新增模块常量与判定，框贴上/下边界即拒绝单目：

```python
_MONO_CLIP_MARGIN_PX = 1.0

def _box_is_clipped(self, det2d, pixel_height) -> bool:
    center_v = det2d.bbox.center.position.y
    top    = center_v - 0.5 * pixel_height
    bottom = center_v + 0.5 * pixel_height
    frame_bottom = 2.0 * self.camera.cy - 1.0      # Detection2D 无图像尺寸 -> 由 cy 推断
    return top <= _MONO_CLIP_MARGIN_PX or bottom >= frame_bottom - _MONO_CLIP_MARGIN_PX
```

2. 新增参数 `mono_depth_classes`（默认 `["person", "bottle"]`），不在白名单的类别**完全禁用单目**：

```python
if self.mono_depth_classes and label not in self.mono_depth_classes:
    return None, "none"          # block 只能靠雷达
```

3. 两个拒绝理由分别标注为 `mono_clipped`（框被裁）与 `none`（类别不适用），便于统计区分。

### 验证结果
- **瓶子扫距（雷达在场，0.3 / 0.5 / 1.0 / 2.0 / 3.0 m）**：全部 `range_source=radar`，
  距离误差 **+0.000 m**，方位误差 **−0.00°**：

  | 场景 | 来源 | 估计 | 误差 |
  |---|---|---|---|
  | bottle @0.30 m | radar | 0.300 m | +0.000 m / −0.00° |
  | bottle @0.50 m | radar | 0.500 m | +0.000 m / −0.00° |
  | bottle @1.00 m | radar | 1.000 m | +0.000 m / −0.00° |
  | bottle @2.00 m | radar | 2.000 m | +0.000 m / −0.00° |
  | bottle @3.00 m | radar | 3.000 m | +0.000 m / −0.00° |

- 饱和 person（1.0 / 2.5 m）与 block（0.8 / 2.0 m）不再输出被信任的错误距离 → **DROPPED**。
- person @5.0 m（未触边）单目照常可用 → **未误杀**。

**通过**。

## 3. P1-1 区分距离来源

### 问题
`det.id` 只有 `"<label>#<detector-source>#<n>"`，**看不出距离是怎么来的** ——
雷达实测回波和单目猜出来的深度在下游完全一样，无法排查、无法按来源降级。

| 场景 | 改动前 | 改动后 |
|---|---|---|
| bottle@0.5 m（雷达） | `bottle#yolo#0` | `bottle#yolo#radar#0` |
| person@5.0 m（单目） | `person#yolo#0` | `person#yolo#mono#0` |
| person@1.0 m（被裁 + `publish_without_range=true`） | `person#yolo#0` | `person#yolo#mono_clipped#0`（x=y=0） |

### 原因
`_make_detection3d()` 构造 id 时只带 label 和 detector source，丢掉了融合阶段刚刚算出来的 `range_source`。

### 修法
`_make_detection3d()` 增加 `range_source` 形参，id 扩展为 4 段：

```python
# "<label>#<detector-source>#<range-source>#<n>"
index = det2d.id.split("#")[-1] if det2d.id else "0"
det.id = f"{label}#{source}#{range_source}#{index}"
```

`range_source ∈ { radar, mono, mono_clipped, none }`。索引取原 id 的**末段**，保持编号语义不变。

**向后兼容已核实**：唯一解析 id 的下游是 `vision_web_stream.py:445`，它取 `parts[0]`/`parts[1]`，
中间插入一段不影响它；`avoidance_decider` / `vision_to_costmap` 不解析 id。

### 验证结果
三种来源（`radar` / `mono` / `mono_clipped`）均可区分，且「无距离」不再伪装成有效测距。**通过**。

## 4. P2-1 补 import + `_angles` 缓存失效判定

### 问题
雷达驱动改变**角度布局**（`angle_min` / `angle_increment` 变化）但**波束数不变**时，
缓存的 `_angles` 不会失效，窗口按错误的角度匹配，直接打到背景墙：

| 场景（雷达开、单目关，唯一来源是雷达） | 改动前 | 改动后 |
|---|---|---|
| 1 @`angle_min=−180°` | 0.300 m ✓ | 0.300 m ✓ |
| 2 @`angle_min=−57.3°` | **7.000 m（+1300%）** | 0.500 m ✓ |
| 3 @`angle_min=−180°` | 1.000 m ✓ | 1.000 m ✓ |
| 4 @`angle_min=−57.3°` | **7.000 m（+250%）** | 2.000 m ✓ |

### 原因
1. 缺少 `from vision_msgs.msg import Detection2D`（`_box_is_clipped` 的类型标注需要）。
2. 缓存判定只看波束数量：

```python
if self._angles is None or self._angles.shape[0] != count:   # 只看 count
    self._angles = msg.angle_min + np.arange(count) * msg.angle_increment
```

`angle_min` 从 −180° 变成 −57.3°、波束数仍是 361 时，`_angles` 保持旧布局 →
物体的 bin 被解算成错误角度 → 窗口找不到目标 → 回落到单目（而单目已被关闭 → 整体丢失）。

### 修法
1. 补 `Detection2D` import。
2. 缓存判定扩展为 **count 变化 OR 角度几何变化**：

```python
if (self._angles is None
        or self._angles.shape[0] != count
        or self._scan_angle_min != msg.angle_min
        or self._scan_angle_increment != msg.angle_increment):
    self._angles = msg.angle_min + np.arange(count) * msg.angle_increment
    self._scan_angle_min = msg.angle_min
    self._scan_angle_increment = msg.angle_increment
```

新增两个状态字段 `_scan_angle_min` / `_scan_angle_increment`。

### 验证结果
布局交替切换（−180° ↔ −57.3°，波束数恒为 361）下，改动后 4 个场景全部命中雷达、误差 0。**通过**。

## 5. P3 融合统计 topic

### 问题
"发布的障碍里到底有多少真的拿到了雷达距离"**在运行时不可观测** ——
只有累计日志，没有可脚本化/可监控的接口。

### 原因
统计只存在于节点内部字典，且日志不区分区间与累计。

### 修法
1. 新增参数 `stats_interval`（默认 1.0）、`fusion_stats_topic`（默认 `/vision/fusion_stats`）。
2. `_stats` 扩展为 7 项：`frames / detections / radar / mono / mono_clipped / dropped / published`。
3. 新增 `_publish_stats()`，以 JSON 形式定时发布（`std_msgs/String`）：

```python
payload = dict(self._stats)
payload["stamp"] = self.get_clock().now().nanoseconds / 1e9
msg = String(); msg.data = json.dumps(payload, sort_keys=True)
self._stats_pub.publish(msg)
```

4. 日志改为**按区间增量**打印（`_stats_logged` 快照做差），避免累计值刷屏。

### 验证结果

```
$ ros2 topic info /vision/fusion_stats
Type: std_msgs/msg/String
Publisher count: 1

$ ros2 topic echo /vision/fusion_stats --once
data: '{"detections": 44, "dropped": 0, "frames": 44, "mono": 0,
        "mono_clipped": 0, "published": 44, "radar": 44, "stamp": ...}'
```
